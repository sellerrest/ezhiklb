# EzhikLB

> Лёгкая web-панель для управления TCP- и UDP-балансировкой на Linux.

**EzhikLB (Ezhik Load Balancer)** объединяет панель управления, переиспользуемые ядра конфигурации и удалённые узлы. Трафик обрабатывается IPVS непосредственно в ядре Linux, а панель отвечает за конфигурацию, health-check, наблюдение и обновления.

Это форк [ezhikdev/ezhiklb](https://github.com/ezhikdev/ezhiklb) с тремя архитектурными изменениями:

1. **Панель переписана на Python** (FastAPI + SQLAlchemy) вместо Go.
2. **Узел (node) больше не подключается к панели** — панель сама дозванивается на локальный API узла. Панели не нужен открытый входящий порт вообще; узел продолжает обслуживать трафик сколько угодно долго, если панель недоступна, и бесшовно подхватывает новую конфигурацию, как только связь восстанавливается.
3. **Профили переименованы в «Ядра»**, редактор структурирован как Входящие/Исходящие, а подключение узла — это один шаг: скрипт на VPS печатает готовый блок для вставки в панель.
4. **База данных на выбор**: SQLite (по умолчанию, один сервер) или PostgreSQL — выбирается при установке панели.

Узел (агент, управляющий IPVS/iptables) остаётся на **Go** — это проверенный, хорошо протестированный код, который не было смысла переписывать; изменился только протокол его общения с панелью.

## Главное

- Входящие с TCP, UDP или обоими протоколами сразу, режим `tcp` (маршрутизация по SNI) или `http` (по SNI и URI-пути);
- Связующие: гибкие правила маршрутизации (равно/содержит/начинается с — и их отрицания) с выбором исходящего по `ping`, `least` или ручным процентам, и affinity для закрепления клиента;
- TCP-пинг health-check на точный адрес:порт каждого исходящего, с автоматическим исключением недоступных;
- одна панель и несколько удалённых узлов, несколько админов (управляются через CLI `ezhik-lb admins`);
- живая статистика: онлайн и трафик (Мбит/с) по каждому входящему и исходящему, не только по узлу целиком;
- одноразовый перезапуск узлов и сброс соединений при публикации ядра;
- графики RAM, CPU, сети и активных IP;
- состояние IPVS, firewall и применения конфигурации;
- обновление подключённых узлов одной кнопкой с проверкой SHA-256, плюс `ezhik-lb update` для самой панели;
- сохранение последней конфигурации на узле: трафик продолжает работать при недоступной панели — панель никогда не находится в пути пользовательского трафика;
- установка панели и узла в один шаг: `curl -fsSL .../bootstrap-panel.sh | sudo bash` и аналогично для узла, systemd или Docker.

## Как устроено

```text
Браузер → Панель (Python) → локальный API узла (Go) → IPVS → Backend-серверы
```

- **Панель** хранит ядра конфигурации, версии, узлы, события и телеметрию, и **сама** периодически обращается к каждому узлу (point 2 форка).
- **Узел** — Go-агент; на первом старте сам генерирует API-ключ и самоподписанный TLS-сертификат, поднимает локальный HTTPS API и печатает данные для подключения. Панель подключается к этому API как клиент — узлу не нужно ничего знать о доступности панели.
- **IPVS** обрабатывает пользовательский TCP/UDP-трафик в ядре Linux.

Панель не находится в пути пользовательского трафика и не открывает никакого входящего порта для узлов. Если она временно выключена, уже применённые правила и health-check продолжают работать на узлах — это гарантирует `Reconciler.Restore()`, который перестраивает IPVS/iptables из последнего сохранённого состояния при каждом старте агента, независимо от связи с панелью. Как только панель снова может дозвониться до узла, она проталкивает новую конфигурацию — существующий дифф-алгоритм применения (add-before-remove, quiesce-before-delete) гарантирует бесшовный переход. Подробности — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Требования

- Debian или Ubuntu `amd64` — как для панели, так и для узлов;
- root или `sudo`;
- для панели: Python 3.11+ (устанавливается автоматически), SQLite или доступ к PostgreSQL;
- для узла: доступ к панели не требуется вообще — узел работает автономно и просто ждёт, пока панель к нему подключится;
- открытые TCP/UDP-порты выбранных входящих на узлах;
- на узле — свободный TCP-порт для локального API агента (по умолчанию `62050`), доступный панели.

## Установка панели

Один шаг, без git clone — скачивает актуальный релиз и ставит сам (нужен
опубликованный релиз, см. `.github/workflows/release.yml`):

```bash
curl -fsSL https://raw.githubusercontent.com/sellerrest/ezhiklb/main/scripts/bootstrap-panel.sh | sudo bash
```

Либо вручную — из уже скачанного релиза или локального билда (`cd web && npm run build`):

```bash
sudo ./scripts/install-panel.sh
```

Установщик спросит:

1. **Доступ к web-интерфейсу** — только локально через SSH-туннель (по умолчанию, рекомендуется) или по сети.
2. **Порт панели** (по умолчанию `8080`).
3. **База данных** — SQLite (по умолчанию) или PostgreSQL (спросит хост/порт/базу/пользователя/пароль).

В отличие от исходного проекта, установщик **не спрашивает отдельный порт API узлов** — панель больше не принимает входящие подключения от узлов, только сама к ним обращается.

Повторный запуск обновляет панель, сохраняя базу и конфигурацию. Перед обновлением создаётся резервная копия в `/var/backups/ezhiklb`. Обновлять проще через `ezhik-lb update` (см. ниже).

Альтернатива systemd-установщику — Docker: `docker compose up -d --build` (см. `docker-compose.yml` и `docker/panel.Dockerfile` в корне репозитория). Выберите один способ, не оба сразу.

## Первый вход

Если панель доступна только локально:

```bash
ssh -L 8080:127.0.0.1:8080 root@IP_ПАНЕЛИ
```

Откройте <http://127.0.0.1:8080> — при первом заходе панель попросит придумать
логин и пароль администратора и сохранит их (пароль — в виде scrypt-хэша) в
своей базе. При следующих заходах вход — по этому логину и паролю.

Панель поддерживает несколько админов, но добавлять/удалять их и менять пароли
можно только через CLI на сервере (`ezhik-lb admins ...`), не через веб —
см. «Управление панелью» ниже.

## Управление панелью

Установщик кладёт на сервер команду `ezhik-lb`:

```bash
ezhik-lb help              # список команд
ezhik-lb stop               # остановить
ezhik-lb restart            # перезапустить
ezhik-lb logs                # логи в реальном времени
ezhik-lb edit-env           # отредактировать переменные окружения
ezhik-lb edit                # отредактировать systemd unit / docker-compose.yml
ezhik-lb admins list         # список админов
ezhik-lb admins add ivan     # добавить админа (спросит пароль)
ezhik-lb admins passwd ivan  # сменить пароль админа
ezhik-lb admins remove ivan  # удалить админа
ezhik-lb update              # проверить и установить новую версию
ezhik-lb uninstall           # полностью удалить панель
```

`admins` — единственный способ добавить второго админа или восстановить
доступ, если пароль забыт; работает напрямую с базой, не зависит от того,
запущена ли сама панель.

## Подключение узла (point 4 форка — один шаг)

На новой VPS — один шаг, без git clone (скачивает готовый бинарник агента из релиза):

```bash
# Обычная установка (systemd)
curl -fsSL https://raw.githubusercontent.com/sellerrest/ezhiklb/main/scripts/bootstrap-node.sh | sudo bash

# Установка в Docker
curl -fsSL https://raw.githubusercontent.com/sellerrest/ezhiklb/main/scripts/bootstrap-node.sh | sudo bash -s -- --docker
```

Либо вручную — из уже скачанного релиза (нужны `bin/ezhiklb-agent` и, для
`--docker`, `docker/node-agent.Dockerfile` рядом со скриптом):

```bash
sudo ./scripts/install-node.sh
sudo ./scripts/install-node.sh --docker
```

Агент сам сгенерирует API-ключ и сертификат и напечатает готовый блок:

```text
Адрес узла:  203.0.113.10
Порт узла:   62050
API ключ:    ‹случайная строка›
Сертификат:
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

Скопируйте этот блок целиком и вставьте его в панели: **Узлы → Добавить узел**, выберите ядро — и всё, узел подключён. Никакого отдельного «сначала имя, потом настройки» — одна форма, одна отправка.

## Ядра (было «Профили»)

**Ядро** — переиспользуемая конфигурация из трёх частей, которую можно назначить нескольким узлам сразу:

- **Входящие** — хост:порт, который узел слушает, режим разбора трафика (`tcp` — только по SNI, `http` — по SNI и URI-пути) и какие протоколы реально слушать (TCP/UDP, можно оба сразу).
- **Исходящие** — серверы назначения (адрес:порт) со своей проверкой жизни (TCP-пинг на этот же адрес:порт — интервал, таймаут, сколько неудач подряд до отключения и удач до возврата).
- **Связующие** — правила маршрутизации: какой входящий с каким исходящим (или несколькими) связан, по каким условиям (SNI/путь: равно, не равно, содержит, начинается с — и их отрицания), с каким affinity и по какой стратегии выбора исходящего, если их несколько (`by ping`, `by least`, ручные проценты).

Откройте **Ядра → Новое ядро**, добавьте хотя бы один входящий и исходящий, свяжите их связующим и опубликуйте — назначенные узлы получат новую версию при следующем опросе панелью (по умолчанию раз в 5 секунд, настраивается на каждом узле отдельно).

При публикации существующего ядра можно включить **«Перезапустить узлы»** — назначенные узлы один раз пересоздадут своё состояние и сбросят связанные соединения.

TCP/UDP через IPVS остаются прежним быстрым путём для простых входящих без правил маршрутизации по SNI/пути; связующие с условиями обрабатывает отдельный L7-прокси узла (SNI-сниффинг для `tcp`, полноценный HTTP-реверс-прокси для `http`).

## Обновление узла

В панели на карточке узла нажмите «Обновить» — панель попросит узел скачать официальный релиз, проверить SHA-256 и атомарно заменить бинарник, затем узел сам перезапускает свой systemd-юнит. Прогресс виден в реальном времени.

## Полезные команды

```bash
# Панель
sudo systemctl status ezhiklb --no-pager -l
sudo journalctl -u ezhiklb -n 100 --no-pager -l
curl -fsS http://127.0.0.1:8080/healthz && echo

# Узел
sudo systemctl status ezhiklb-agent --no-pager -l
sudo journalctl -u ezhiklb-agent -n 100 --no-pager -l
sudo cat /var/lib/ezhiklb-agent/state.json
sudo cat /var/lib/ezhiklb-agent/enroll/connection.txt   # данные подключения ещё раз
sudo ipvsadm -Ln
sudo ipvsadm -Ln --stats
```

## Безопасность

- Для публичного доступа закройте панель HTTPS через Caddy/nginx или держите её только за SSH-туннелем — она не общается с узлами через тот же порт, так что закрывать его от узлов не нужно.
- Связь панели с узлами всегда идёт по TLS с закреплённым (pinned) сертификатом: панель доверяет ровно тому сертификату, который узел напечатал при установке — никакого центра сертификации не требуется, но и подменить узел без приватного ключа сертификата нельзя.
- Не публикуйте пароль администратора и API-ключи узлов. Пароль хранится в базе панели только в виде scrypt-хэша; API-ключи узлов — в открытом виде, поскольку панель обязана предъявлять их узлам при каждом обращении.
- Регулярно сохраняйте `/etc/ezhiklb`, БД панели и `/var/lib/ezhiklb-agent` на каждом узле.
